# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Qué es esto

TaraTrack: tracker personal de series/pelis (tipo TVTime/Trakt) autoalojado, un único usuario. FastAPI + Jinja2 + htmx, server-rendered, sin build step de frontend. SQLite embebido.

## Comandos

```bash
pip install -r requirements.txt
TMDB_API_KEY=... TARATRACK_SECRET_KEY=... TARATRACK_PASSWORD=... TARATRACK_DB_PATH=./taratrack.db uvicorn app.main:app --reload
```

**Tests y linter (desde la ronda 2026-08-21)**: `pytest -q` (12 tests, `tests/test_repo.py` + `tests/test_login.py`) y `ruff check .` (config en `pyproject.toml`, solo revisión — reglas deliberadamente pocas: imports/variables sin usar, sintaxis, orden de imports, nada de estilo/opinión que choque con patrones ya asumidos como `except Exception` ancho a propósito). **El propio repo vive en un montaje CIFS (`TaraNAS`) que no soporta symlinks** — `python -m venv` falla ahí con `Operation not supported` al crear `lib64`. El venv de desarrollo vive fuera del repo, en `/home/tara/.venvs/taratrack` (local, btrfs) — usarlo con `/home/tara/.venvs/taratrack/bin/pytest -q` en vez de `python -m venv .venv` dentro del propio checkout.

- Import inicial desde un export de Trakt: `TRAKT_EXPORT_DIR=/ruta/json python3 scripts/seed_from_trakt.py` (idempotente, nivel título) + `scripts/import_history_from_trakt.py` (historial episodio a episodio → `episodes.watched_at`) + `scripts/import_extra_from_trakt.py` (favoritos rankeados + notas → comentario, episodios puntuados → favoritos, y repara fechas de visionado pisadas). `scripts/resync_anime_characters.py` migra en bloque personajes cacheados como actores TMDB a personajes AniList preservando favoritos por nombre. En el servidor los JSON se meten al contenedor con `docker cp` (el código va horneado en la imagen, no montado). Ninguno pisa ni duplica al repetirse.
- Backup (se ejecuta en el host del servidor, no dentro del contenedor): `scripts/backup.sh`.

## Arquitectura

Capas: `app/main.py` (raíz de composición FastAPI: crea la app, monta estático/middleware, incluye los routers, y se queda con lo transversal — auth, arranque, tareas de fondo, manejo de errores) → `app/routers/*.py` (rutas HTTP por dominio, ver "Split de módulos" más abajo) → `app/repo/` (paquete con todas las queries SQL, sin ORM, dividido por subsistema) → `db.py` (conexión sqlite3 + `SCHEMA` + `MIGRATIONS` + `INDEXES`; WAL + `busy_timeout` para que la sync de fondo no bloquee a la app). `app/web.py` (templates Jinja2 + filtros compartidos) y `app/matching.py` (heurística de emparejamiento TMDB/AniList) son infraestructura compartida entre routers, sin rutas propias. `app/config.py` centraliza toda lectura de variables de entorno. Clientes externos: `tmdb.py` (API de TMDB en `language=es-ES` — los títulos cacheados antes del cambio quedan en inglés, `_is_anime` y `_GENRE_ES` contemplan ambos idiomas; búsqueda, detalles, episodios, recomendaciones, créditos, descarga de pósters/fotos a `app/static/{posters,profiles}`; la búsqueda de `/buscar` reintenta con el título canónico de AniList si TMDB no devuelve nada) y `anime.py` (Jikan/MyAnimeList con fallback AniList, gratis y sin API key: metadatos para altas manuales y **personajes de anime** — `get_characters` da la imagen del personaje, no del actor real; `sync_characters` la usa cuando los géneros TMDB incluyen Animation, con TMDB de fallback, y el botón "Recargar" del detalle fuerza `resync_characters` en títulos cacheados con la lógica vieja).

**Todo el código sigue usando `from app import repo; repo.funcion(...)` exactamente igual que antes del split** (ver "Split de módulos" en Seguridad más abajo) — `app/repo/__init__.py` reexporta explícitamente los 185 nombres originales (incluidos los privados con `_`), así que ningún caller (rutas, scripts, tests) tuvo que tocarse.

Sincronización: `repo.sync_library` (sin argumento: abre **una conexión por título** a propósito — con una sola transacción larga la BBDD quedaría bloqueada minutos para la app) refresca metadatos de todo lo seguido y los episodios de las series en emisión. La llaman el botón "Sincronizar" de `/calendario` y una tarea de fondo (`sync_loop` en `main.py`, `asyncio.to_thread` cada `SYNC_INTERVAL_HOURS = 12`) — no hace falta sincronizar a mano en el uso normal.

Detalle de título: la sección "Similares" (`get_similar`, hasta 10 de TMDB incluyendo ya vistos, con enlace interno si están en BBDD) se carga lazy vía htmx (`hx-trigger="load"`) para no meter la latencia de TMDB en el render de la página. El enlace "Ver tráiler" (`tmdb.get_trailer`, `/titulo/{tmdb_id}/{type}/trailer`, `partials/trailer.html`) sigue el mismo patrón lazy — pide `/videos` de TMDB en español y si no hay ningún tráiler de YouTube cae a inglés (muchos solo están subidos en el idioma original); si no encuentra nada en ninguno de los dos, el partial no renderiza nada (sin aviso de "sin tráiler", simplemente no aparece el botón). Es un link de salida a YouTube, no un reproductor embebido — mantiene la filosofía de "sin JS de más" del proyecto.

Modelo de datos (`db.py`):
- `titles` — cacheado desde TMDB por `tmdb_id`. Los títulos sin match en TMDB (altas manuales, `repo.create_manual_entry` desde el formulario de `/buscar`) usan un `tmdb_id` sintético **negativo**; cualquier código que asuma `tmdb_id > 0` para llamar a la API real debe filtrar estos casos (ver `list_trackable_titles`, `sync_episodes`, `sync_characters`). `runtime_minutes` en series es **minutos por episodio** (con fallback al runtime del último episodio emitido, `episode_run_time` suele venir vacío); la duración total es `runtime_minutes × episode_count` (ver `DURACION_TOTAL_SQL` para el orden por duración de `/vistas`).
- `entries` — 1:1 con `titles`, es el estado de seguimiento de Tara: `status` (`pending`/`watched`), `rating`, `comment`, categorías opcionales (`cat_historia`, `cat_animacion`, `cat_personajes`, `cat_musica`, `cat_disfrute`).
- `episodes` — tiene `comment` e `is_favorite` propios (comentar/marcar episodios sueltos desde `partials/episode_row.html`). Alimenta `/calendario` (grid por día estilo Trakt, hoy primero, días pasados plegados, y **solo series empezadas** — ≥1 episodio visto), `/historial` (unión cronológica de episodios vistos + títulos marcados + rewatches, `list_history`) y el carrusel "Continuar viendo" de inicio (`list_continue_watching` sobre `_HOME_SHOWS_SQL`): **cualquier** serie con ≥1 episodio visto y emitidos por ver, da igual el `status` de la entry (The Boys a medias cuenta aunque esté marcada vista y no emita ahora). Las no empezadas NO salen en el carrusel, viven en la lista de pendientes (ordenable, `ORDENES_PENDIENTES`). El check de cada tarjeta (`POST /entrada/{id}/siguiente`) marca visto el `next_unwatched_episode`; el doble check (`POST /entrada/{id}/todos`, con `hx-confirm`) marca todos los emitidos de golpe — ambos re-renderizan `partials/home_card.html` vía htmx. Para que el carrusel conozca los "que faltan" de series importadas de Trakt, `sync_library` hace una pasada única de episodios en series empezadas sin `air_date` cacheado. Nota: el `show_status = 'Returning Series'` de TMDB NO significa "en emisión" (sigue activo entre temporadas); "en emisión de verdad" = episodios en ±21 días.
- `characters`/`favorite_characters`, `watch_sessions` (rondas de "Volver a ver", ver abajo), `lists`/`list_items` (la lista "Favoritos" es la `is_default = 1`, ver `get_default_list`; renombrar/borrar listas solo para las no-default). Cada lista tiene un buscador embebido ("Añadir títulos a esta lista", `GET /lista/{id}/buscar` + `POST /lista/{id}/anadir/...`, `add_entry_to_list` es INSERT OR IGNORE, no toggle) para llenarla sin pasar por `/buscar`. `/waifus` tiene su propio buscador en bloque sobre los personajes **ya cacheados** (`search_characters_local`, LIKE por nombre) para poner estrellas sin ir ficha a ficha. El orden manual (flechas subir/bajar) es genérico: `_move_in_ranking` normaliza posiciones y las intercambia, y lo usan tanto `move_list_item` (`list_items.position`) como `move_waifu` (`favorite_characters.position` — la página `/waifus` es el ranking global de personajes con estrella, de cualquier título). `/estadisticas` (`get_stats`) es todo SQL local, con `_GENRE_ES` para unificar géneros cacheados en inglés y en español.
- Columnas añadidas después del `CREATE TABLE` inicial van en `MIGRATIONS` como `ALTER TABLE` idempotente (capturando `duplicate column`) — no editar `SCHEMA` para columnas nuevas sobre una tabla ya desplegada, añadir aquí.
- `duels` (`table_name, winner_id, loser_id, result`) + `elo_snapshots` (`table_name, item_id, elo, rank, snapshot_at`, PK compuesta) sostienen el ranking por duelos — `elo` vive como columna en cada tabla comparable (`list_items.elo`, `favorite_characters.elo`, `entries.elo`), nunca en `duels`/`elo_snapshots`, que solo son historial/foto. Ver "Ronda 2026-08-13" más abajo para el motor completo (`random_duel_pair`, `record_duel`, `duel_coverage`, `reset_elo`, `get_elo_deltas`).
- `titles.original_language`, `titles.anilist_id`, `titles.anilist_genres`, `titles.anilist_studio` — rellenados por `tmdb.get_details` (idioma) y `anime.match_anilist_basic`/`get_seasonal_anime` (AniList), usados por `_IS_ANIME_SQL` y por la predicción "% que te gustará" del calendario de temporada (ver más abajo). Ninguno se rellena en el `INSERT`/`UPDATE` original de todo lo cacheado antes de esta ronda — hace falta re-sync/backfill para que converjan.

**"Marcar vista" en una serie marca el primer episodio, no la serie entera** (decisión explícita de Tara 2026-08-12, tras preguntar y confirmar que así lo quería): `mark_watched_quick(conn, entry_id, title_row)` pone `entries.status = 'watched'` y además marca `next_unwatched_episode` (normalmente T1E1 — reutiliza la misma función que el check individual de la tarjeta de inicio, así que respeta `season_number > 0` y episodios ya emitidos). La ruta `/vista/{tmdb_id}/{type}` sincroniza episodios primero si hace falta (`sync_episodes` si `list_episodes` viene vacío) para tener de qué elegir. Si Tara ya se ha visto la serie entera, el flujo esperado es: marcar vista (marca T1E1, la serie entra en "Continuar viendo") → doble tick de la tarjeta para marcar el resto de golpe. **No confundir con marcar TODA la serie de una vez** — eso sigue siendo el doble tick, a propósito.

Rewatch ("Volver a ver", rediseñado 2026-08-12, comportamiento de fondo rediseñado otra vez 2026-08-20 estilo Trakt): en la ficha de algo visto hay un único botón "Volver a ver" (`POST /entrada/{id}/volver-a-ver`, `repo.start_rewatch`). Registra una ronda en `watch_sessions` (la columna `speed` es herencia del diseño anterior y queda en su default; `notes` ya no se pide) y guarda `entries.rewatch_started_at = ahora` — **ya NO desmarca (borra) ningún episodio**, así que ninguna fecha del visionado anterior se pierde nunca, ni siquiera al re-marcar el mismo episodio otra vez (ver "Ronda 2026-08-20" más abajo para el detalle completo del motor: `episode_watches`, `_pending_clause`, `_log_episode_watch`/`_unlog_episode_watch`). La serie vuelve a "Continuar viendo" desde T1E1 igualmente — `_HOME_SHOWS_SQL` trata como "pendiente otra vez" cualquier episodio con fecha ANTERIOR a `rewatch_started_at`, en vez de exigir `watched_at IS NULL`. La nota, el comentario y el `watched_at` original de la entry no se tocan; `count_plays` = 1 + rondas.

**El personaje "en gris" no es spoiler de nada** — es `/static/img/sin-portada.svg` (fondo `#2a2e3a`, texto "Sin portada" en `#9a9dab`), el placeholder genérico cuando no se encontró foto (AniList/MAL/TMDB no tenían imagen para ese personaje, o el nombre no casó bien). Tara preguntó si el gris marcaba personajes muertos — no hay ninguna lógica de ese tipo en el código, ni la habrá sin pedirlo expresamente (sería fácil confundirlo con spoiler real). Si aparecen muchos grises en un título, es que el reparto cacheado tiene huecos, no información oculta.

Personajes que faltan: el sync automático solo trae el top 25 de AniList del título (Black Clover tiene 500), así que la ficha y `/waifus` tienen un buscador de personajes por nombre — `anime.search_characters` prueba AniList primero y, si no lo conoce (p.ej. "Secre Swallowtail", que en AniList está como "Kuro Nero" — nombres localizados distintos entre fuentes), cae a MyAnimeList vía Jikan (`_search_jikan_characters`, con 3 reintentos — Jikan da 504 con frecuencia, a veces en rachas largas). Devuelve `(resultados, jikan_caido)` para que la plantilla distinga "no existe ese personaje" de "prueba en un rato, MyAnimeList no responde" — no tratar una lista vacía como "no encontrado" sin mirar el segundo valor. Alta con `repo.add_character_manual`: id positivo = AniList (prefijo `al_`), id negativo = MAL (prefijo `mal_`, el id se guarda en negativo para no chocar con ids de AniList en la misma tabla). Desde `/waifus`, un personaje externo solo se puede añadir si `repo.match_library_title` encuentra su anime en la biblioteca (exacto por nombre, si no por prefijo — para casar subtítulos de temporada tipo "Black Clover: ...") — el personaje necesita un título al que colgarse.

**"No me acuerdo de nada, 5 y ya"** (`POST /puntuar/{entry_id}/no-recuerdo`, botón en `review_queue.html`): relleno explícito de un toque — nota 5.0 y comentario `-` — para vaciar la cola de puntuar en lo importado de Trakt sin memoria real, sin pasar por el examen. Distinto de "Paso, no me acuerdo" (que solo salta el título en esta ronda sin puntuarlo). **Cuidado al probar esto en desarrollo: aplica una nota real e irreversible-por-defecto a una entry real** — no usarlo contra datos de producción sin revertir después si es solo una prueba (pasó una vez, se revirtió a mano).

**Dónde discrepas con la crítica** (`/discrepancias`, `repo.get_rating_discrepancies`): compara `entries.rating` con `titles.vote_average` (misma escala 1-10) sobre lo puntuado, dos listas de 10 — mayor diferencia positiva (le encanta lo que la crítica no) y mayor diferencia negativa. Enlazado desde `/estadisticas`.

**Progreso por temporada** (`title_detail.html`, dentro de la sección Episodios): una barra por temporada (`episodes|selectattr("watched_at")|list|length` sobre `seasons` en el contexto ya existente, sin tocar la ruta) — cálculo puramente en plantilla, no hay columna ni query nueva. Junto a la barra, si la temporada no está completa, botón **"✓ Temp. completa"** (`POST /titulo/{tmdb_id}/{type}/temporada/{season_number}/marcar`, `repo.mark_season_watched`) — mismo patrón que `mark_all_aired_watched` (el doble tick de la tarjeta de inicio) pero acotado a `season_number`, para tragarse una temporada de una sentada sin marcar la serie entera ni ir episodio a episodio. Solo toca episodios ya emitidos (`air_date <= today`); si la temporada no ha empezado a emitir, el botón no hace nada (no se oculta por eso, solo por `vistos == total`).

**Mosaico** (`/mosaico`, `repo.list_all_posters`): todas las portadas con imagen real (excluye placeholder) en una rejilla densa (`auto-fill, minmax(80px,1fr)`), sin texto, cada una enlaza a su ficha. Puramente visual — accesible desde el menú "Más" del móvil, sin entrada en el `topnav` de escritorio (mismo criterio que Waifus/Ajustes, no saturar la nav principal).

**Reevaluar una nota** (al fondo del todo de `title_detail.html`, solo si `entry.status == 'watched'`): un bloque con la misma clase `.exam-q.rated` que las preguntas del examen (pedido explícito de Tara, "misma paleta"), enlaza a `/marcar-vista/{tmdb_id}/{type}?volver=ficha` — la ruta ya soportaba reeditar (precarga rating/comment/categorías de la entry existente, `mark_watched` hace `UPDATE` sin más), lo único que faltaba era el punto de entrada visible y volver al sitio correcto tras guardar. `marcar_vista_submit` ahora distingue tres destinos por `volver`: `puntuar` → `/puntuar`, `ficha` → `/titulo/{tmdb_id}/{type}`, cualquier otro (incluido vacío) → `/vistas` (comportamiento de siempre). Si se añade un cuarto sitio desde el que reevaluar, seguir este patrón — no asumir que solo hay dos destinos. El campo "¿Cuándo la viste?" del formulario (`mark_watched.html`) se oculta también con `volver == "ficha"`, no solo `"puntuar"` — Tara: "se supone que valoro algo que ya está valorado", no tiene sentido pedir fecha de visionado al reevaluar algo ya marcado. Al ocultar el campo, `watched_date` simplemente no viaja en el POST y `mark_watched` conserva el `watched_at` original vía `COALESCE` — no hizo falta tocar el backend, solo la plantilla.

**Quitar nota** (`POST /entrada/{entry_id}/quitar-nota`, `repo.clear_rating`, debajo del bloque "Reevaluar" en `title_detail.html`, solo si `entry.rating is not none`): pone `rating` y las 5 `cat_*` a `NULL` sin tocar `status` ni `comment` — la entry sigue `watched` (no desmarca como vista) y vuelve a caer en la cola de `/puntuar`. Pensado para notas puestas antes de tiempo (Tara: "he puntuado dos 10 y aún no se ha acabado la serie"). Confirmación en dos pasos (`<details class="del-confirm">`, mismo patrón que "Borrar lista") por ser destructivo — se pierde el número si no está anotado en otro sitio.

**`/vista/{tmdb_id}/{type}` (marcar vista rápido) ahora tolera que `sync_episodes` falle**: antes, un hipo de red al pedir episodios (para saber cuál es "el primero" a marcar en una serie nunca vista) tumbaba la ruta entera con un 500 — se vio en vivo durante pruebas de esta sesión. `try/except` alrededor de esa llamada: si falla, la entry se marca vista igual, sin episodio marcado (se puede marcar a mano después desde la ficha). Mismo criterio que `/buscar/resultados` — ninguna llamada a TMDB dentro de una ruta debe poder tumbar toda la petición sin un fallback razonable.

**`/puntuar` excluye series aún en emisión** (`repo._NO_EN_EMISION_SQL`, usado en `count_review_queue` y `next_review_item`): filtra `titles.show_status = 'Returning Series'` — Tara: "no quiero valorar antes de que se acabe la serie/temporada". Mismo campo que ya se documentaba como poco fiable para "está emitiendo ahora mismo" (`in_season`/±21 días en `_HOME_SHOWS_SQL`), pero aquí el matiz es distinto: no importa si está emitiendo *esta semana*, importa si TMDB ya la dio por **terminada** — "Returning Series" significa que no, aunque esté entre temporadas. Las pelis (`show_status` siempre `NULL`) no se ven afectadas (`COALESCE(..., '') != 'Returning Series'`). Depende de que `show_status` esté razonablemente al día — lo refresca `sync_library` cada 12h para todo lo trackeado, no hace falta sincronizar a mano para que el filtro funcione bien.

Flujo de puntuación: marcar como vista puede ser "rápido" (`mark_watched_quick`, sin nota) o "con nota" (`mark_watched`). Lo marcado rápido cae en la cola de `/puntuar` (`repo.next_review_item`, orden aleatorio con `ORDER BY RANDOM()`, con parámetro `excluir` en la URL para poder pasar de un título sin puntuarlo dentro de la misma ronda). En el formulario, "el examen" (las categorías) es la vía principal y la nota directa queda plegada como alternativa; la nota final es o bien la media ponderada de categorías (`CATEGORY_WEIGHTS` en `repo.py`, pasados a la plantilla como `data-weight` para la vista previa en vivo — no duplicar los pesos en JS) o bien el número directo — nunca las dos cosas a la vez.

**Resumen anual** (`/resumen?anio=`, `yearly.html`, `repo.get_year_stats`/`get_available_years`, 2026-08-12): todo por **fecha real de visionado** (`watched_at`), no por cuándo se añadió el título — episodios/pelis vistas ese año, series con actividad, tiempo total, mes más activo, top 5 géneros y top 5 mejor valorados **puestos** ese año (por `entries.watched_at`, no por año de estreno del título). `get_available_years` descarta años `< 1980` para filtrar la fecha placeholder `1970-01-01` que queda en historial importado sin fecha real. Selector de año como `.sort-bar` de enlaces, no un `<select>` — consistente con el resto de filtros de la app.

**Exportar datos** (`GET /ajustes/exportar`, `repo.export_data`): vuelca a JSON descargable (`Content-Disposition: attachment`) solo lo que Tara curó a mano — notas, comentarios, categorías, listas, waifus — **no** el caché de TMDB (posters, overview, etc., no aporta como copia personal). Pensado como copia propia independiente del backup de la BBDD, no como export/import real (no hay ruta de importación, es de solo lectura para él).

**Backup diario al NAS** (fuera del repo, en el PC de escritorio de Tara, no en el servidor): `~/.local/bin/taratrack-backup-sync.sh` + timer de systemd de usuario (`~/.config/systemd/user/taratrack-backup-sync.{service,timer}`, `OnCalendar=*-*-* 09:00:00`, `Persistent=true`) copian por `scp` el backup del día (creado por `scripts/backup.sh` en el servidor a las 4:00) a `/home/tara/TaraNAS/Taratara/TaraTrack/Backup/`, manteniendo los **7 más recientes** (`KEEP=7` en el script). **Corre desde el PC de Tara, no desde el servidor** — el servidor no tiene el NAS montado (solo el PC de Tara, vía CIFS), así que tirar de `scp` desde donde ya está todo montado y con SSH de sobra evitaba crear una relación de confianza nueva servidor↔NAS solo para esto. `Persistent=true` es la red de seguridad: si el PC está apagado a las 9:00, se pone al día en el próximo arranque/login en vez de saltarse el día. Si el PC lleva varios días apagado seguidos, el backup nocturno de 14 días del propio servidor sigue siendo la copia real de seguridad — esto es una copia adicional en el NAS, no la única.

Recomendaciones (`/recomendados`, `repo.list_recommendations`): personalizadas, no populares — 8 semillas al azar entre lo puntuado ≥8.5 o en Favoritos, `tmdb.get_recommendations` por semilla **en paralelo** (`ThreadPoolExecutor`, ver más abajo — las 8 no dependen unas de otras), descarta todo lo ya presente en `titles` **y todo lo baneado** (`rejected_recommendations`, ver abajo), rankea por cuántas semillas coinciden (hasta 40, filtro Mix/Series/Pelis); cada tarjeta enseña "Porque te gustó X" y enlace a la ficha (poster+título → `/titulo/{tmdb_id}/{type}`, que auto-crea la entry como pending al abrirla si no existía — mismo mecanismo que en toda la app, deshacible con el toggle de "+ Pendientes"). La sinopsis NO va en la tarjeta — Tara la quería en la ficha técnica, no en la "ficha mini" — ver `title_row.overview` en `title_detail.html`. "Otra tanda" recarga con otras semillas.

**BAN de recomendados** (`rejected_recommendations`: `tmdb_id` UNIQUE, `type`, `title`, `poster_path`) — llamado "BAN" en la UI, no "No me gusta" (Tara: "es literal un ban, ponlo"). `POST /recomendados/rechazar` (formulario con inputs ocultos, no `hx-vals` con interpolación directa — un título con comillas rompería el JSON) inserta y hace desaparecer la tarjeta vía htmx; se filtra en `list_recommendations` sumándolo al set `known`. **Solo afecta a recomendados** — un título baneado se sigue pudiendo buscar y añadir normal en `/buscar` (confirmado explícitamente con Tara, no tocar esa separación). Gestionable desde `/ajustes` (`settings.html`, deliberadamente sin entrada visible en la nav de escritorio salvo un icono de engranaje pequeño al final del `topnav` — está también en el menú "Más" del móvil) — `POST /ajustes/rechazados/{id}/quitar` deshace un ban.

**"+ Pendientes" es un toggle, no solo un alta** (`POST /pendiente/{tmdb_id}/{type}`, `partials/entry_actions.html`): si la entry ya está en pending, la quita entera (`repo.remove_pending_entry` — borra también `list_items`/`favorite_characters`/`watch_sessions` que cuelguen de ella antes de borrar la entry, o petaría por FK) en vez de quedarse en un botón `disabled` sin salida. Pensado para deshacer altas por error (p.ej. abrir la ficha de una recomendación solo para mirarla, o una prueba añadida a una lista). Solo aplica a `pending` — lo `watched` no se borra así, se gestiona desde su ficha. **El "quitar" pasa por confirmación en dos pasos** (`GET /pendiente/{tmdb_id}/{type}/confirmar` → estado `pending_confirm` con "¿Quitar? Sí"/"No"; el "No" es `GET /pendiente/{tmdb_id}/{type}/estado`, que relee el estado real en vez de asumir "pending") — pedido tras un roce real en `/pendientes` (fácil tocar el botón sin querer haciendo scroll en el móvil). **`/buscar` refleja el estado real de la biblioteca** (`repo.get_entry_states`, llamado desde `buscar_resultados`): antes cada resultado se renderizaba siempre como `state="new"`, así que un título ya visto y en Favoritos (p.ej. La nota de internet (`vote_average`) se enseña también en lo NO visto: filas de pendientes, resultados de búsqueda, Similares y Recomendados (en búsqueda/similares/recomendados sale del `_normalize` de `tmdb.py`, que incluye `vote_average`).

El doble tick de la tarjeta de inicio (marcar todos los episodios emitidos) NO usa `hx-confirm` — el diálogo `window.confirm()` del navegador no salta en el móvil de Tara, así que la petición nunca llegaba a lanzarse. **Rendimiento de `tmdb.py`**: dos cosas que sí importaban ("va lento" era real, no percepción — TMDB está en internet, no en la LAN, así que la latencia es de red, y antes se pagaba en serie). (1) `httpx.Client` compartido a nivel de módulo (`_client`) en vez de `httpx.get()` suelto en cada llamada — reutiliza conexión keep-alive, evita renegociar TLS en cada petición. (2) `ThreadPoolExecutor` (`_pool`, 8 workers) para llamadas independientes: `search()` pide `/search/tv` y `/search/movie` en paralelo, `get_details()` pide detalle + `external_ids` en paralelo, y `repo.list_recommendations` pide las 8 semillas en paralelo (su propio `ThreadPoolExecutor`, no el de `tmdb.py` — son llamadas de `repo`, no de `tmdb`). Todas son I/O-bound (esperando red), así que el hilo suelta el GIL y el paralelismo es real, no cosmético.

**La ficha técnica iba lenta la primera vez que se abría un título** (Tara: "abrir la ficha técnica va lento"): `sync_episodes` pedía los episodios de cada temporada **en serie** (una serie de 12 temporadas = 12 llamadas seguidas a TMDB) y `sync_characters` descargaba las ~15-25 fotos del reparto **en serie** también. Las dos se paralelizaron con `ThreadPoolExecutor` (fetch/descarga en hilos, el `INSERT` a SQLite se queda secuencial en el hilo principal después — sqlite3 no es thread-safe para compartir la misma conexión entre hilos). Probado con una serie de 12 temporadas nunca vista: **1 segundo** en frío (antes habría sido varios segundos, quizá más de 10 con reparto grande). Para un título ya cacheado (visita repetida) no cambia nada — `sync_episodes`/`sync_characters` ya hacían un chequeo `existing`/`list_episodes` y no volvían a llamar a la API.

**`refresh_metadata` ahora también corrige título/sinopsis/géneros en inglés**: antes solo refrescaba nota/duración/próximo episodio, así que un título cacheado antes del cambio a `language=es-ES` se quedaba en inglés **para siempre**, ni la sync de fondo cada 12h lo arreglaba. Ahora `UPDATE titles SET title = ?, overview = ?, genres = ?, ...` en cada refresco — un `repo.sync_library()` (botón "Sincronizar" o la tarea de fondo) ya corrige lo viejo solo. Se lanzó una sync manual completa el 2026-08-12 (874 títulos, 39.6s con las llamadas paralelas) para arreglarlo de golpe en vez de esperar 12h.

**Bloque 2 completo (2026-08-14, resto de pasos tras el techo p85 de arriba) — motor completo del índice de afinidad.** Sustituye del todo al perfil de "nota media" anterior. Arquitectura:

- **`repo._load_affinity_raw(conn)`** carga TODA la materia prima en memoria en una sola pasada de SQL (titles+entries con `anilist_*`, episodios vistos, rewatches, listas, personajes favoritos, última temporada puntuada por título, duelos) — así el backtesting (recalcular el perfil UNA VEZ POR CADA título puntuado, ver abajo) no golpea la BBDD cientos de veces, solo reagrega en Python sobre los mismos datos.
- **`repo._aggregate_affinity(raw, cfg, exclude_entry_id=None)`** es el núcleo: por atributo (género/tag/estudio) calcula las señales de **APETITO** (volumen — log de episodios agrupados por franquicia vía union-find sobre `anilist_prequel_ids`, con tope `FRANCHISE_EPISODE_CAP=300`—, lift, ritmo, día1, rewatch, curación) y **CALIDAD** (techo p85, suelo p25, disfrute, media suavizada, corrección Elo), normaliza cada señal a **percentil comparando el atributo con el resto de atributos del usuario** (`_percentile_rank`), suaviza SOLO las señales de calidad hacia el neutro (50) por confianza — el eje apetito son conteos/ratios de consumo, ya moderados por volumen de datos al percentilizar, suavizarlos también no tenía sentido matemático claro y se descartó — y combina con **media geométrica + castigo al desfase**: `base = apetito^0.6 · calidad^0.4`, `afinidad = base · (1 − 0.5·max(0,apetito−calidad−25)/100) · confianza`. `exclude_entry_id` es el leave-one-out del backtesting: saca ESE título de TODOS los conteos (no solo de la nota), evitando que el sistema se "acuerde" de su propio consumo.
- **Franquicias**: solo hay datos de precuela DIRECTA por título (`anilist_prequel_ids`, filtrado a `PREQUEL`/`PARENT` en `anime.py`), nunca `SEQUEL` — `_franchise_roots` usa union-find sobre un grafo NO dirigido para que temporada 1 y temporada 3 caigan en la misma franquicia aunque solo estén enlazadas 3→2 y 2→1.
- **Lift**: cuota de consumo (episodios vistos con A ÷ total) frente a cuota de "catálogo" — aproximado como toda la biblioteca backfilleada (vista+pendiente), no el catálogo completo de AniList, que no está indexado localmente. Las películas (sin filas en `episodes`) cuentan como 1 "unidad vista" para no perder señal de consumo.
- **Día1**: solo cuenta episodios de títulos con `show_status = 'Returning Series'` (aproximación de "se seguía en emisión" — no hay histórico real de eso), dentro de 7 días del `air_date`; un título ya terminado queda simplemente SIN señal (nunca en negativo), tal como pedía el encargo. **Ritmo y día1 solo usan fechas `>= 1980-01-01`** (mismo corte que `get_available_years` — el filtro real de placeholders vive ahí, no en `list_history` como decía el encargo original; localizado por criterio real, no por la referencia literal).
- **Corrección Elo**: solo con ≥4 títulos con ≥5 duelos jugados (`entries.elo`, pool de `/duelo`) — diferencia de puesto por nota vs puesto por Elo, dentro de ese conjunto.
- **Rechazo NO implementado a propósito**: el encargo pedía "baneados de A ÷ veces que A apareció en recomendados", pero no existe ningún registro de qué géneros/tags aparecieron en recomendados (`rejected_recommendations` no guarda atributos AniList) — construirlo exigiría instrumentar nuevas "impresiones" en `/recomendados`, fuera del alcance de este bloque. - **IDF de tags** (`_compute_tag_idf`): `ln(N/n_tag)` sobre toda la biblioteca backfilleada. `predict_score` pondera cada tag por `rank_en_la_obra × IDF`.
- **Tabla `taste_profile`** (una fila por atributo, todas las señales crudas + apetito/calidad/inercia/afinidad/confianza/n_títulos/n_episodios) y **`score_distribution`** (un `raw_score` por título puntuado, del backtesting) — ambas recalculadas SOLO por `repo.recompute_taste_profile(conn)`, nunca en una petición HTTP. `build_taste_profile` ahora es una lectura pura de `taste_profile` (rápida, para cada carga de página).

## Diseño visual y UI/UX

Directrices traídas por Tara (2026-08-21) para guiar cualquier trabajo visual futuro sin tener que repetirlas cada vez. ### 1. Visión y filosofía de producto
- **No es un panel de administración ni un gestor CRUD.** Es una app de entretenimiento personal de nivel producto final / consumidor (referencias de acabado: AniList, Letterboxd, Linear, Plex).
- **La imagen es la protagonista:** portadas y contenido multimedia mandan, los metadatos son secundarios.
- **Tema único, solo Dark Mode** — paleta Tararch Warm Dark, ya implementada en `app.css` `:root`: fondo `--bg:#0f0f0f`, superficie `--surface:#161616`, acento `--accent:#ff9e64`, texto `--text:#c9c9c9`/`--text-bright:#ffffff`. Prohibido meter colores fuera de esta paleta.

### 2. Jerarquía espacial y superficies (profundidad)
- Prohibido el diseño 100% plano — 3 capas:
  1. Fondo (`--bg`).
  2. Superficie / tarjetas (`--surface`, bordes sutiles `rgba(255,255,255,0.08)`, no grises duros).
  3. Elevación / modales / cabecera hero (`--surface-elevated`, con `--shadow`).
- **Estado real:** capas 1 y 2 ya existen como variables. La 3ª no existe como variable propia todavía — antes de tocar CSS de modales/hero, comprobar si ya hay un valor hardcodeado equivalente en uso (candidatos: cabecera de ficha técnica elevada de la ronda 2026-08-20) y unificarlo en `--surface-elevated`, no crear una variable duplicada.
- **Control de lectura:** contenedores al 96% para rejillas de portadas, pero bloques de texto continuo (sinopsis, notas) con `max-width: 70ch`.

### 3. Hardware objetivo y jerarquía de dispositivos
1. **PC principal (máxima prioridad):** ASUS ROG Strix 27" QHD (2560×1440, 255Hz) y ASUS 24" FHD (1920×1080, 120Hz). Transiciones fluidas de alta tasa de refresco (`cubic-bezier(0.16, 1, 0.3, 1)`). Rejillas `auto-fit` sin huecos muertos en pantalla ancha.
2. **iPhone 17 Pro (único móvil objetivo):** Dynamic Island y `safe-area-inset-*` (incluido landscape) — ya implementado. Zonas táctiles mínimas de 44px. Navegación en `bottomnav`, sin depender de `:hover`.
3. **ROG Strix G15 15.6" (Tararch):** altura de cabeceras controlada para 15.6". Affordance visual en carruseles para trackpad/ratón.

Un solo comando (`scripts/deploy.sh` desde la raíz del repo) hace, en orden: `py_compile` de todo `app/`+`scripts/`, `ruff check` (informativo, no bloquea), `pytest` (saltable con `--skip-tests`, solo para iterar rápido — nunca para el despliegue real), `scripts/check_templates.py` (compila las plantillas Jinja2 en seco con el `Environment` real de la app, no con stubs), y el balanceo de llaves de `app.css` — **todas las comprobaciones que ya se hacían a mano en cada ronda de este fichero, ahora automatizadas antes de tocar el servidor**. Si todo pasa: snapshot `.tar.gz` fechado del `app/` actual del servidor en `deploy-snapshots/` (se conservan los últimos 5 — la única red de seguridad real que existe sin git), `rsync -av --delete` (el `--delete` es a propósito: la estructura del repo ya cambió de raíz una vez, con el split de módulos), build + `docker rm -f` + `up -d`, y espera hasta 30s a que `/login` responda 200 antes de darse por bueno — si no, imprime los últimos logs y aborta. `scripts/deploy.sh --rollback` restaura el snapshot server-side más reciente y reconstruye, sin tocar el NAS. Los pasos manuales de abajo siguen siendo correctos como explicación de qué hace el script por debajo (y como plan B si el script no estuviera disponible), pero **el comando real a usar es `scripts/deploy.sh`**, no copiarlos uno a uno.

```bash
rsync -av /home/tara/TaraNAS/Taratara/TaraTrack/app/ servidor:/home/tara/taratrack/app/
ssh servidor "cd /home/tara/taratrack && docker-compose build taratrack"
ssh servidor "docker rm -f taratrack && cd /home/tara/taratrack && docker-compose up -d"
```

El `docker rm -f` antes de `up -d` es necesario: el `docker-compose` del servidor es v1.29.2 (EOL) y recrear el contenedor in-place a veces revienta con `KeyError: 'ContainerConfig'`.

**HTTPS** (2026-08-12): `tara.series` fuerza SSL con un certificado **autofirmado**, no Let's Encrypt — `tara.series` es un dominio interno (solo lo resuelve el DNS rewrite de AdGuard, no existe en internet), así que Let's Encrypt no puede validarlo por HTTP-01/TLS-ALPN-01. Certificado generado con `openssl req -x509 -newkey rsa:2048 -days 3650 -addext "subjectAltName=DNS:tara.series"` (10 años, así no hace falta tocarlo) y subido a NPM como certificado "Custom" (`provider: "other"`, API `/api/nginx/certificates` + `/upload`), luego `ssl_forced: true` en el proxy host. El navegador avisará de certificado no confiable la primera vez en cada dispositivo — es autofirmado a propósito, no roto; confiar en él manualmente si molesta el aviso. HSTS deliberadamente **desactivado** (con un autofirmado, forzar HSTS podría dejar el sitio inaccesible si el cert da problemas más adelante).

Los datos persistentes (BBDD, pósters, uploads, perfiles) viven en volúmenes Docker con nombre (`taratrack-data`, `taratrack-posters`, `taratrack-uploads`, `taratrack-profiles`) — un rebuild de `app/` nunca los toca. La app solo escucha en `127.0.0.1:8420` del servidor, detrás de Nginx Proxy Manager como reverse proxy.
